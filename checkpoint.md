# Affiliate Course Platform — Checkpoint Plan

This file is the **single source of truth for project continuity across sessions/accounts**.
It exists because this build is too large for one Claude session/credit budget, so it's split
into checkpoints that can each be completed by a *different* Claude account, in sequence.

Read this together with `spec1.md` (the full product spec). `spec1.md` never changes.
This file **does** change — every checkpoint's completion updates the Progress Log at the bottom.

---

## 0. How the handoff works

Each time you (the human) start a new checkpoint with a fresh Claude account, give that
session **all three** of these:

1. `spec1.md` — the full spec (unchanged, always included)
2. `checkpoint.md` — this file (**always the latest version**, including the updated Progress Log
   from all prior checkpoints)
3. A zip/folder of **all files produced so far** (every prior checkpoint's output, not just the
   immediately previous one — later checkpoints often need earlier files, e.g. DB config)

Then give the new session this prompt (copy-paste, editing the bracketed part):

> I'm building the project described in spec1.md, following the plan in checkpoint.md.
> Checkpoints 0 through [N-1] are already complete — their files are attached and their status
> is logged in checkpoint.md's Progress Log. Please complete **Checkpoint [N]: [title]** only.
> Don't start on later checkpoints. When done, give me all new/modified files, and give me an
> updated checkpoint.md with the Progress Log entry filled in for this checkpoint (status, files
> produced, any deviations or decisions you made, anything flagged for me to confirm).

**Rules for whoever executes a checkpoint (instructions to the executing Claude, embedded here
so it survives the handoff):**

- Do **only** the scope listed under that checkpoint. Do not "helpfully" start the next one —
  that's what blows the credit budget for the account after you.
- Follow the **Global Conventions** section below exactly (naming, folder layout, env var names)
  so files from different checkpoints/accounts still fit together without a refactor pass.
- If a checkpoint turns out too big to finish in one go, stop, split it into `N.1`, `N.2` in the
  Progress Log, and hand off the remainder rather than doing a rushed partial job.
- At the end, always:
  1. List every file created/modified this checkpoint.
  2. Fill in that checkpoint's row in the **Progress Log** (status, date, files, notes/deviations,
     open questions for the human).
  3. Output the *entire* updated `checkpoint.md` as a file so it can be passed to the next account.
- Never silently change a decision made in an earlier checkpoint (e.g. a table schema, an env var
  name). If a prior decision looks wrong, flag it in Progress Log notes and ask the human —
  don't just change it, or later checkpoints (done by other accounts) will break.

## 1. Global conventions (locked in at Checkpoint 0, binding for all later checkpoints)

> Checkpoint 0 fills these in concretely. Everyone after that follows them as-is.

- **Repo/folder structure:**
  ```
  src/
    config/       env loading + validation, Postgres pool
    routes/       Express routers, one per resource area, thin (route wiring only)
    controllers/  request handlers — empty until Checkpoint 2+
    models/       DB query functions per table — empty until Checkpoint 1+
    middleware/   auth/admin gating, error handling, etc.
    utils/        shared helpers (encryption, validation, etc.) — empty until needed
    app.js        Express app construction (middleware stack + route mount)
    server.js     process entry point (DB check, listen, graceful shutdown)
  migrations/     node-pg-migrate migration files (Checkpoint 1+)
  seeds/          one-time seed scripts (Checkpoint 1+)
  uploads/        local disk storage, KYC docs / profile photos — never served via
                  express.static, always through a protected/ownership-checked route
  ```
  Full detail and rationale in the project's own `README.md` (Checkpoint 0 deliverable) —
  treat that README as authoritative if this summary and it ever disagree.
- **Naming conventions:**
  - JS files: `camelCase.js`; resource-scoped files use a dotted suffix by layer —
    `auth.routes.js`, `auth.controller.js` (Checkpoint 2+), `user.model.js` (Checkpoint 1+).
  - Folders: lowercase, no separators.
  - Postgres tables: `snake_case`, plural. Finalized list (Checkpoint 1): `users`, `admins`,
    `courses`, `purchases`, `reward_transactions`, `withdrawals`, `kyc_type_a`, `kyc_type_b`,
    `fraud_flags`, `password_reset_tokens`, `lectures`. See README.md's "Database schema" section
    for what each table holds and the key design decisions behind it.
  - Postgres columns: `snake_case`.
  - API routes: versioned, kebab-case, all under `/api/v1/...`, grouped by resource
    (`/api/v1/auth/...`, `/api/v1/user/...`, `/api/v1/wallet/...`, `/api/v1/kyc/...`,
    `/api/v1/admin/...`, `/api/v1/courses/...`).
  - Env vars: `SCREAMING_SNAKE_CASE`.
- **Env var list so far:** `NODE_ENV`, `PORT`, `DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN`,
  `COOKIE_SECRET` (all in `.env.example`, which also documents vars expected from later
  checkpoints so nobody picks a different name by accident: `AES_ENCRYPTION_KEY` (CP4),
  `PAYMENT_GATEWAY_MODE` (CP3), `PAYOUT_GATEWAY_MODE` (CP5), `CAPTCHA_SECRET_KEY` (CP2),
  `MAIL_SERVICE_API_KEY` (CP2), `ADMIN_2FA_ISSUER_NAME` (CP8)). `.env.example` is
  append-only — never rename/remove an existing key without flagging it here first.
- **Code comment style:** every file commented per spec's "other devs can pick this up"
  requirement — see any Checkpoint 0 file for the expected density/tone (a file-header
  block explaining purpose + key decisions, plus inline comments on non-obvious logic).
- **DB access:** raw `pg` driver + `node-pg-migrate` for schema migrations, not a full ORM.
  Rationale: small fixed schema, and the reward engine (CP3) needs auditable, explicit
  `BEGIN`/`COMMIT` transactions across multiple wallet credits per purchase — see README.md
  "Database access — decision & rationale" for the full writeup. Changing this later is a
  decision to flag here, not to do quietly.
- **How mock gateways are structured:** not built yet, but the intended shape is documented
  in README.md so Checkpoints 3/5 don't have to re-derive it: `src/services/payment/` and
  `src/services/payout/`, each exporting one function (`charge(...)` / `payout(...)`) behind
  a single interface, with the mock as the only registered implementation for now, selected
  via `PAYMENT_GATEWAY_MODE` / `PAYOUT_GATEWAY_MODE`. Swapping to a real gateway later means
  adding a new implementation behind the same interface, not touching calling code.
- **Frontend tooling (decided Checkpoint 10, not locked in before then):** plain HTML/CSS/
  vanilla JS, no build step/bundler/framework, served as static files from the same Express
  process/origin as the API (`public/` directory, `express.static()` in `app.js`) — so every
  frontend `fetch()` uses a relative `/api/v1/...` path. Full reasoning in README.md's
  "Frontend tooling decision" section. This was Checkpoint 10's own call for the PUBLIC
  frontend specifically — Checkpoints 11/12 should default to the same choice for consistency
  but may reasonably re-evaluate given their own interactivity needs (charts, live tables);
  see that same README section.
- **Logging/sensitive data:** binding on every future checkpoint — request logging
  (morgan) only logs method/URL/status, never the body; error messages must stay generic
  when they touch KYC/financial fields (never log the actual Aadhaar/PAN/account number
  value, even in an error). See README.md for detail.

## 2. Checkpoint list

Each checkpoint is scoped to roughly "one cohesive subsystem, a handful of files, completable by
a normal user's message/credit allowance in one sitting." If a checkpoint feels too big once
you're in it, split it (see rules above) rather than pushing through.

### Checkpoint 0 — Project scaffolding & conventions
**Goal:** Nothing functional yet — just the skeleton everything else builds on.
- Node/Express project init, folder structure (routes/controllers/models/middleware/config)
- Postgres connection setup (`pg` or an ORM — decide and document why)
- `.env.example` with all known env vars so far
- Base `package.json`, scripts (start/dev)
- README documenting folder structure + conventions (this becomes the reference for Section 1 above)
- Empty/placeholder route files for the major areas (auth, user, admin, wallet, kyc, courses) so
  later checkpoints know exactly where to add code
**Deliverables:** scaffolded repo, README, `.env.example`
**Not in scope:** any real business logic, DB schema, auth logic

### Checkpoint 1 — Database schema & seed scripts
**Goal:** Every table the whole app needs, plus the one-time seed data.
- Full schema: `users`, `admins`, `courses`, `wallets`/wallet fields, `referrals` (or referrer_id
  on users), `transactions`/purchases, `withdrawals`, `kyc_type_a`, `kyc_type_b`, `fraud_flags`,
  whatever else the spec implies
- Migration files (or raw SQL) + a migration runner
- Seed script: 6 fixed courses with correct prices/reward splits from the spec table
- Seed script: `COMPANY` system account (refer code `COMPANY`)
- Seed script: 2 admin accounts (placeholder email/password, one-time, not via UI)
**Deliverables:** migration files, seed scripts, schema diagram/notes in README
**Depends on:** Checkpoint 0

### Checkpoint 2 — User auth (signup/login, non-admin)
**Goal:** A user can sign up and log in; referral chain gets recorded (but reward math is NOT
built yet — that's Checkpoint 3).
- Signup endpoint: refer code (defaults to `COMPANY`), course selection, all signup fields,
  bcrypt password hashing, self-referral block, unique email/phone constraint enforcement
- Login endpoint: JWT in httpOnly cookie
- Rate limiting on signup/login (per IP)
- Basic CAPTCHA hook (stub is fine if no real service chosen yet — flag this)
- Forgot-password flow: emailed reset link with expiring token (email sending can be a stubbed/
  logged "would send email" if no mail service is wired up yet — flag this)
- Refer-code generation logic (unique per user)
**Deliverables:** auth routes/controllers/middleware, JWT middleware for protected routes
**Depends on:** Checkpoints 0, 1

### Checkpoint 3 — Purchase, mock payment gateway, and the referral reward engine
**Goal:** The core money logic of the whole product. This is the checkpoint to be most careful
and most conservative with scope on — do not blend in KYC/withdrawal work.
- Mock payment gateway module (interface designed so a real gateway drops in later)
- Purchase endpoint: buy a course → mock payment → on success, wallet crediting
- **2-tier reward engine**, implemented exactly per the spec's worked example: walk up from the
  buyer's own chain fresh on every purchase (direct referrer, then that referrer's referrer);
  reward table keyed to the course *purchased*, not the buyer's or referrer's own course;
  COMPANY fallback whenever a tier has no valid recipient
- Company's own cut recorded (per the "Company" column in the course table) — clarify where this
  goes (its own ledger vs COMPANY wallet) and flag the decision
- Unit tests / manual test cases replicating the spec's User1–User4 worked example, since this is
  the easiest place for silent bugs
**Deliverables:** purchase route, reward engine module, mock payment module, test cases
**Depends on:** Checkpoints 0, 1, 2

### Checkpoint 4 — KYC
**Goal:** KYC submission for both types, encrypted at rest, masked in UI-facing responses.
- Type A (bank) and Type B (UPI) submission endpoints
- Format validation (PAN regex, Aadhaar 12-digit, IFSC regex)
- AES-256 field-level encryption for Aadhaar/PAN/account number, key from env var
- Masking logic for any endpoint that returns these fields (last-4-only outside entry/admin view)
- Confirm nothing KYC-related ever hits logs (audit the logging middleware/error handler)
- Auto-approval on submit (no review queue needed)
**Deliverables:** KYC routes, encryption/masking utility module
**Depends on:** Checkpoints 0, 1, 2

### Checkpoint 5 — Wallet & withdrawals
**Goal:** Withdraw flow, mock payout gateway, solvency tracking.
- Withdrawal endpoint, gated on the relevant KYC type being complete
- Mock payout gateway module (same interface-swap pattern as the payment gateway)
- State machine: `pending` → `processing` → `paid`/`failed`, with wallet balance NOT deducted on
  `failed`
- Withdrawal history endpoint
- Admin-facing aggregate: running total of unwithdrawn wallet balance across all users
**Deliverables:** withdrawal routes, payout module, wallet balance query helpers
**Depends on:** Checkpoints 0, 1, 2, 4 (needs KYC gating), 3 (needs wallet balances to exist)

### Checkpoint 6 — Course content delivery
**Goal:** Lecture management + protected access.
- Admin-side data model already exists from Checkpoint 1; here: endpoints to add/edit/reorder
  lectures (title, video link, order, description) per course
- User-side: list lectures for a course **only if the user owns it**
- Protected route pattern (not public static) reused later for KYC docs/photos too — build the
  reusable "protected file/route" middleware here since this is its first use case
**Deliverables:** lecture CRUD routes (admin), lecture-list route (user), ownership-check middleware
**Depends on:** Checkpoints 0, 1, 2

### Checkpoint 7 — User dashboard data APIs
**Goal:** All the read-heavy endpoints the sidebar pages need. No frontend yet — just APIs.
- Dashboard: revenue today/7d/30d/all-time, revenue chart data, recent referrals list w/ search
- Affiliate links: per-owned-course shareable link generation/lookup
- Upgrade: list of unowned courses
- Leaderboard: top earners today/7d/30d/all-time
- Profile: get/update endpoints (name, email, phone, state, photo — photo goes through the
  protected-route pattern from Checkpoint 6)
**Deliverables:** dashboard/affiliate/leaderboard/profile routes
**Depends on:** Checkpoints 0, 1, 2, 3, 6

### Checkpoint 8 — Admin backend (separate auth + panel APIs)
**Goal:** Everything admin-side, kept fully separate from user auth.
- `admins` table auth (already seeded in Checkpoint 1) — separate login route/endpoint
- 2FA (TOTP) setup screen + login flow using `speakeasy`/`otplib` + `qrcode`
- Admin JWT middleware, rejects any non-admin token on `/admin/*`
- Course management CRUD (name/description/price/reward splits)
- User management (view/add/deactivate)
- Visibility endpoints: KYC submissions, withdrawal history, referral trees, fraud-flag alerts
**Deliverables:** admin auth + 2FA, admin panel API routes
**Depends on:** Checkpoints 0, 1 (heavily), plus read access into 3/4/5/6/7's data

### Checkpoint 9 — Fraud/abuse baseline
**Goal:** The smaller cross-cutting protections, easiest to bolt on once auth exists.
- Same-IP/device signup detection → fraud flag record (visibility only, no auto-block)
- Confirm rate limiting from Checkpoint 2 covers login too, not just signup
- Wire fraud flags into the admin visibility endpoint from Checkpoint 8
**Deliverables:** fraud-flag detection logic, admin surfacing
**Depends on:** Checkpoints 1, 2, 8

### Checkpoint 10 — Public/pre-login frontend
**Goal:** Landing, course listing/detail, signup, login, legal placeholder pages.
- Dark/professional theme, design direction inspired by the two reference sites (note: reference
  sites can only be used for *inspiration/UX patterns*, not copied assets/branding/copy)
- Signup form wired to Checkpoint 2's endpoint (refer-code auto-fill from URL param)
- Login form wired to Checkpoint 2
- Placeholder Privacy/Terms/Refund pages, clearly marked "placeholder — replace before going live"
**Deliverables:** public-facing pages/components
**Depends on:** Checkpoint 2 (and ideally 0 for whatever frontend tooling is chosen there)

### Checkpoint 11 — Authenticated dashboard frontend
**Goal:** The 8 sidebar pages, wired to Checkpoints 3–7's APIs.
- This is likely the single biggest checkpoint — consider splitting into 11a (Dashboard,
  Affiliate Links, My Courses, Upgrade) and 11b (Leaderboard, Wallet, KYC, Profile) up front
**Deliverables:** authenticated app shell + all sidebar pages
**Depends on:** Checkpoints 2, 3, 4, 5, 6, 7

### Checkpoint 12 — Admin panel frontend
**Goal:** UI for everything built in Checkpoint 8/9.
**Deliverables:** admin login (incl. 2FA UI), admin dashboard pages
**Depends on:** Checkpoint 8, 9

### Checkpoint 13 — Integration pass, deploy prep
**Goal:** Wire loose ends, not new features.
- End-to-end smoke test of signup → purchase → reward crediting → withdrawal
- HTTPS/Certbot setup notes for the Hostinger VPS
- Final `.env.example` review (every var from every checkpoint present)
- Confirm mock→real gateway swap points are actually clean (payment + payout)
- Resolve the two open flags from spec1.md: refund policy decision, OTP/email-verification gap
**Deliverables:** deploy notes, final env template, smoke-test checklist
**Depends on:** everything above
